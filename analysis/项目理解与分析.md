# Study-Review / Cram Engine 项目理解与分析

> 分析时间：2026年
> 项目仓库：review/

---

## 一、项目定位

**Study-Review（期末速成引擎 / Cram Engine）** 是一个基于 Claude Code Skill 生态的 AI 驱动期末复习工具。目标用户是大学生，核心场景是考前一两周内快速消化课程重点、考点，避免挂科。

一句话概括：**把学习科学原理工程化为一套 LLM 流水线**——不依赖 AI"聪明地教"，而是通过四阶段拆分 + 严格流程控制 + 进度持久化，让 AI 稳定地扮演一个按学习科学方法论行事的辅导老师。

---

## 二、核心设计理念

### 2.1 多步流水线替代巨型 System Prompt

将复杂教学任务拆分为四个阶段，每阶段模型指令单一聚焦。这样做的原因是：LLM 对复杂指令的遵循度会随 prompt 长度衰减，拆分后每个阶段的输出更稳定、更可靠。

### 2.2 学习科学内置于流程，而非依赖 Prompt

认知负荷控制、精细加工、生成效应、检索练习等策略通过阶段顺序和子步骤自然实现，而不是写在 prompt 里期望模型自行理解。

### 2.3 其他设计原则

- **终端优先**：纯 Claude Code 终端交互，slash command 触发，零 UI 开发（核心引擎层面）
- **配置文件驱动复用**：课程信息、考点列表、题型、偏好一次性写入 YAML，多轮复用
- **进度持久化**：每个课程独立进度文件（Markdown），支持中断恢复
- **数据本地化**：不注册、不付费，所有数据存在本地 `~/.cram-engine/`

## 三、四阶段流水线

```
┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│  阶段1   │ → │  阶段2   │ → │  阶段3   │ → │  阶段4   │
│  拆解    │    │  讲授    │    │  检题    │    │  补漏    │
│  ~5%     │    │  ~50%    │    │  ~25%    │    │  ~15%    │
└──────────┘    └──────────┘    └──────────┘    └──────────┘
```

### 阶段1 — 拆解（总时间 ~5%）

**输入**：课程配置中的 `must_know`（必考点）+ `key_points`（扩展点）

**任务**：将每条重点拆为独立知识点（约5分钟讲完），按逻辑顺序排列（概念 → 属性 → 关联 → 应用 → 局限）。标注记忆钩子类型：

| 钩子类型 | 含义 |
|---------|------|
| `acronym` | 适合缩写口诀记忆 |
| `contrast` | 与另一概念易混淆，需对比表 |
| `absurd` | 抽象易忘，用荒诞场景锚定 |
| `none` | 直接讲即可 |

**输出**：知识点树，写入进度文件。展示知识点总数和分布，等待用户确认（回车全讲 / 先攻必考点 / 跳过指定编号）。

**确认选项**：
- 回车 → 全部按序进入阶段2
- "先攻 must_know" → 只学核心考点
- 指定编号（如"跳过 9, 10, 13"）→ 移除对应知识点（移除 must_know 前警告）

### 阶段2 — 讲授（总时间 ~50%）

每个知识点执行四步教学法：

```
第1步：Concrete First → 第一句必为具体场景，不能以定义开头
第2步：Chunking       → ≤3个关键块，逐块讲，块间暂停确认
第3步：Elaboration    → 追问"这跟之前学的X有什么关系"
第4步：Generation     → 核心概念不给标准定义，先反问用户试总结
```

**记忆强化**：根据阶段1标注的 hook 类型选用口诀 / 对比表 / 荒诞场景。

**节奏控制**：
- 每讲完 3 个知识点暂停一次，展示已学清单，询问节奏
- 用户可说"继续 / 加速 / 减速 / 跳过 / 再讲一遍"
- "跳过" = 停止阶段2，直接进阶段3（跳过的点在阶段3仍按分级策略抽样出题）
- "再讲一遍" = 换场景、换例子、换角度重讲，不重复原话
- must_know 全部讲完后展示里程碑提示："核心考点全部讲完，还剩 N 个扩展知识点"

### 阶段3 — 检题（总时间 ~25%）

**出题策略**（Skill 层直接控制，不依赖模型判断）：

| 考点级别 | 出题逻辑 |
|----------|----------|
| must_know | 每种题型全覆盖 |
| key_points | 每点随机 1-2 种题型，优先选择题 + 情景题 |
| must_know 为空 | 全部考点按 key_point 处理 |

**四个子模式**（按用户配置的题型自动匹配）：

| 子模式 | 覆盖题型 | 批改方式 |
|--------|---------|---------|
| A | 选择、判断 | 逐题对错 + 一句话解析。陷阱题额外揭晓混淆逻辑——干扰项全部来自同一门课其他知识点 |
| B | 案例分析 | 踩分点清单逐项对照（识别理论 → 解释机制 → 给建议） |
| C | 情景知识应用 | 先评理论识别对不对，再评分析逻辑自不自治 |
| D | 名词解释、简答、论述、辨析、填空等 | 对照内部答案逐项核对，指出遗漏点 |

**陷阱题设计**：干扰项全部来自同一门课的其他知识点，防止用户凭排除法猜对。

### 阶段4 — 补漏（总时间 ~15%）

只处理阶段3答错或不确定的点。四步循环：

```
1. 诊断根因 → 概念混淆 / 理解偏差 / 记忆遗漏 / 迁移失败
       ↓
2. 换讲法   → 混淆给对比表 / 偏差给极端反例 / 遗忘换钩子 / 迁移失败给新场景
       ↓
3. 重测     → 出1-2道新题（must_know 答错额外多3道题）
       ↓
4. 顽固判定 → 二次错误标为顽固点，建议隔天再攻（不继续死磕）
```

**结束输出**：已纠正数、顽固点清单、所有 must_know 考点掌握状态（✅已掌握 / ⚠️顽固点 / ❌未纠正）。

## 四、内嵌的学习科学原理

这些不是装饰词，每个都对应引擎的具体行为：

| 原理 | 在引擎中的体现 |
|------|--------------|
| **认知负荷控制** | 阶段1先把知识拆成树，阶段2每次只讲一个、每个不超过三块 |
| **精细加工** | 阶段2讲完追问"这跟你刚学的X有什么关系"，建立知识关联 |
| **生成效应** | 阶段2核心定义不直接给，先让用户试总结再对照纠正 |
| **检索练习** | 阶段3是必过环节，学完马上考，不是可选的 |
| **间隔效应** | 顽固点不在当场死磕，标出来隔天再攻 |
| **元认知监控** | 每3个点暂停问节奏；检题后区分"真错"和"猜对" |

### 5.2 两层架构

项目实际分两个层次：

**核心引擎层（cram-engine-main）**：纯 Claude Code Skill，通过 `/cram` 命令在终端中运行。所有教学逻辑、流程控制、进度管理都在这里。这是项目的灵魂。

**桌面 UI 层（stitch_cram_engine）**：14 个独立的 HTML 页面（Tailwind CSS + Material Symbols + Google Fonts），构成一套完整的桌面应用 UI 原型。每个模块由一个 `code.html` 和一个 `screen.png` 组成。设计风格统一——"Scholar's Study"暖白主题色 (#FAFAF7)，紫色主色调 (#5e39e0)，Material Design 3 色彩体系。

## 六、配置文件规范

### 6.1 课程配置（YAML）

```yaml
course: <课程名称>

must_know:           # 老师明确说必考的
  - 考点1
  - 考点2

key_points:          # 老师划了重点但未强调必考
  - 考点A
  - 考点B

exam_types:          # 考试题型（不绑定具体考点）
  - 选择/判断
  - 案例分析
  - 情景知识应用

materials:           # 教材与资料
  textbook: <教材名称版本>
  slides: <PPT来源>
  notes: <额外笔记>

preferences:         # 教学偏好（有默认值，用户无需手写）
  language: 中文
  tone: 先给一句话核心结论再展开，拒绝学术黑话
  teaching_methods: [concrete_first, chunking, elaboration, generation]
  memory_hooks: [acronym, contrast_table, absurd_example]
  exam_tactics: [keyword_mining, trap_awareness, framework_building]
  example_domains: [大学社团/学生会, 小组作业, 宿舍矛盾, 实习/兼职, 选课与绩点]
  pacing:
    check_in_frequency: every_3_points
    reteach_trigger: "再讲一遍"
```

### 6.2 进度文件（Markdown）

```markdown
# <课程名> - 学习进度

## 状态：<阶段N>-进行中

## 阶段1完成 ✅
- 生成 N 个知识点

## 阶段2进度
- [x] 知识点1 ✅
- [x] 知识点2 ✅
- [ ] 知识点3 ← 下次从这里继续

## 阶段3
- [x] 选择题：4/4 正确
- [x] 案例分析：通过
- [ ] 情景题：未做

## 阶段4
- [x] 知识点X 已纠正（概念混淆→对比表→重测通过）
- [ ] 知识点Y 顽固点 → 建议明天

## 顽固点
- 知识点Y（已尝试2次，建议明天再攻）
```

## 七、命令行接口

| 命令 | 行为 |
|------|------|
| `/cram <课程名> start` | 从阶段1开始。配置不存在时自动进入7步创建流程 |
| `/cram <课程名> resume` | 从进度文件中断处继续 |
| `/cram <课程名> status` | 显示当前阶段、已学/未学数、错题数、顽固点数 |
| `/cram <课程名> retry <知识点>` | 对指定知识点执行微型 讲→测→补 闭环，结果追加不覆盖 |
| `/cram <课程名> summary` | 输出考前清单：must_know 掌握状态、顽固点汇总、建议复习列表 |

### 学习过程中的交互

| 用户输入 | 引擎反应 |
|---------|---------|
| 继续 | 正常节奏 |
| 加速 | 精简版（跳过 generation 步骤） |
| 减速 | 每个点多配一个例子 |
| 跳过 | 停止当前讲授，直接进阶段3 |
| 再讲一遍 | 换场景、换角度，不重复原话 |

## 八、适用与不适用的课程

### ✅ 适合

期末以名词解释、简答、论述、概念辨析为主的课——得分关键是体系清楚、记得住。

| 学科领域 | 举例 |
|---------|------|
| 经管 / 文史哲 / 法学 / 教育学 | 全部概念类课程 |
| 医学 | 解剖学、生理学、病理学、药理学 |
| 计算机 | 计算机网络、操作系统、计算机组成原理（概念部分） |
| 电子 / 通信 | 通信原理、信号与系统（性质与变换对比） |

### ⚠️ 概念+计算混合型

引擎梳理概念框架，但计算大题仍需自己刷题。

### ❌ 不适合

纯数学（高数、概率论、线性代数）、计算+画图主导（数电、结构力学）、编程/设计课。

## 十、项目的亮点与局限

### 亮点

1. **学习科学原理的工程化落地**：六条原理（认知负荷、精细加工、生成效应、检索练习、间隔效应、元认知监控）不是挂在 README 里的营销词，而是硬编码在四阶段流程控制中，不依赖模型自行理解。

2. **容错设计到位**：
   - 用户说"再讲一遍"→ 换讲法而非重复原话
   - 顽固点不持续死磕 → 建议隔天再攻（间隔学习 > 集中死磕）
   - must_know 全题型覆盖，key_points 抽样节省时间

3. **可恢复性**：进度文件实时更新为 Markdown，关终端随时走，回来 resume 继续。

4. **教学风格可定制**：偏好配置中的 `example_domains`（例子坐标系）很有特色——全部绑定大学生日常生活场景（社团、小组作业、宿舍矛盾、绩点博弈），确保举例贴近用户。

5. **诚实的范围说明**：README 明确列出适用与不适用的课程类型，不做虚假承诺。

6. **UI 原型完整**：stitch_cram_engine 的 14 个模块覆盖了从首页到工作台、从题库到导出的完整用户旅程，设计语言统一。

7. **首次使用体验流畅**：7步交互式配置创建流程，每次只问一个问题，用户无需手写 YAML。

### 局限

1. **依赖课程配置质量**：如果用户无法提供课程重点和考试题型，引擎退化为通用 AI 问答。
2. **仅验证于定性知识密集型课程**：纯定量课（概率论、计量经济学）效果未知。
3. **不替代刷题**：选择题/情景题的量远不及真正的题库。
4. **阶段2的多层认知策略在极端情况下可能有遗漏**：处理方式是用户说"按教学模板重讲一次"触发重试。
5. **UI 层为静态原型**：stitch_cram_engine 的 HTML 文件是纯静态页面，尚未与引擎核心打通。
6. **不接受 PDF/Word/PPT/图片作为资料输入**：仅接受 .txt 或 .md 格式的笔记。

## 十一、总结

**Cram Engine 解决的核心问题是**：知识量大、结构复杂、需要理解记忆，但靠自己整理效率太低的考前突击场景。

它本质上是一个**学习科学的操作系统**——不依赖 AI 的"教学天赋"，而是通过精心设计的四阶段流水线、严格的分级出题策略、基于诊断的补漏机制，让 LLM 可重复地、稳定地扮演一个称职的辅导老师。

项目的工程化程度较高，从 SKILL.md 的工作流定义到 design-spec.md 的设计文档，再到 stitch_cram_engine 的 UI 原型，层次分明、文档齐全。尤其值得称道的是，设计者清楚地知道 AI 的边界在哪里——用流程保证下限，不赌模型的上限。
